# Voice agent (`src/voiceAgent/`)

Implementation overview. The design and its rationale are in [voice-agent-design.md](./voice-agent-design.md) (§14.1 is implementation progress); pairing, the agent cursor, and the worker file lock are in [voice-pair-agent-cursor.md](./voice-pair-agent-cursor.md) (§11 is the file lock). Speech services and settings are in [voice.md](./voice.md); sentence read-aloud/translate is in [sentence-replay.md](./sentence-replay.md).

Main classes: `WorkerController`, `VoiceAgent`, `VoiceLlm`, `HostToolRouter`, `WorkerDigest`, `FloorArbiter`, `ResearchRunner`, `VoiceMode`, `conversation.reduce`, `TtsClient`, `VoiceTranscriptStore`, `VoicePanel`, `ReplayPlayer`, `SpeechCache`, `Translator`.

## UI

- **Toggle and status** live in the status bar above the session composer (`src/webview/voiceBar.ts`). The voice agent's avatar and status text on the left switch the tab between the worker conversation and the Bot view; the phone button on the right starts voice mode and, while it is on, hangs up. In voice mode the composer's mic shows the level and acts as mute. In the Bot view the composer always sends to the voice agent: like speech while voice mode is on, as a text chat (`say`) while it is off. The host drives these through `VoiceChatControls` (implemented by `SidebarProvider`).
- **Bot view.** Conversation, a one-line header with the engines in use (short model names, full LLM / STT / TTS config on hover) and the voice LLM's context use (`ctx N%`), and under it context usage (meter, percent, tokens / window), token use per service (LLM: calls, input, output and cost; Cache: read, write and hit rate `cacheRead / (input + cacheRead + cacheWrite)`, when there were any; STT requests, audio sent and tokens when the server reports them; TTS requests, characters and audio), one short row each like the worker's model status, and per-turn Timing are shown in the session tab's Bot view ([design §11.2](./voice-agent-design.md#112-bot-view-content)). Context use is omp's `get_session_stats` figure for the loaded voice context while the voice agent runs; otherwise, for a past conversation or with voice mode off, it is the last LLM call's tokens (input + output + cache read + cache write) against the context window `VoiceLlm` records with every call (`VoiceCallUsage.contextWindow`, from `get_state` at start); transcripts from before that field existed show no context row until their next call. The icon left of the tab title (chat bubble ↔ robot) switches that tab's body between the transcript and the Bot view. The host `VoicePanel` sends/receives through `BotViewSurface` (implemented by `SidebarProvider`, `TabState.botView`); the frontend is `src/webview/voicePanel.ts`, mounted on `.bot-host` in `main.ts`, styled by `styles/chat/voice.css`; message types in `src/shared/voiceViewProtocol.ts`. Tool cards in the Bot view: see [chat-rendering.md](./chat-rendering.md#tool-cards-in-the-bot-view).
- **Welcome.** A new conversation's empty Bot view shows the voice agent's avatar and name, what it does (real-time voice, editor awareness, code edits and terminal, directing the worker, research), one row each for speech-to-text and text-to-speech (short model and server from the view state's `engines`; a green check when its readiness is ok, a red cross with the reason and an "Open Settings → Voice" link when it is not set up or failing, a spinner while it is being checked; the chat's `stateSync` `voiceReadiness` reaches it through `setVoicePanelReadiness`; a click on a row opens Settings → Voice), and, while voice mode is off, a "Call" button (`callVoiceAgent` in `voiceBar.ts`, the phone button's start); with voice mode on, a hint for the phase (listening, muted, standby). A past session with no turns says so instead (`introHtml` and `startHtml` in `voicePanel.ts`). The intro and Call button are also the chat's empty state when every tab is closed: `voiceIntro`, kept up to date like the welcome, which `chat/layout.ts` puts over Open worker and Resume a session ([tabs-and-tui.md](./tabs-and-tui.md)). There the Call button sends `callInNewTab` (a new tab, then voice mode once its worker is ready), and with voice mode on it is left out. Its service rows and phase come from the snapshots, so `SidebarBotView.isBotViewVisible` counts that empty state as the Bot view shown and the host keeps posting them.
- **Attached images.** Images attached in the composer go to the voice model as image parts and show on an image card under the user's message, not as `[name]` in its text (other attachments keep their `[name]`). `toVoiceAttachments` (`src/pi/pendingAttachments.ts`) splits them into `imageFiles` (name and path); the transcript saves them by path on the user entry (`images`). `VoicePanel.snapshot` adds each image's `src`, a webview URI from `BotViewSurface.imageSrc`: the chat webview's `localResourceRoots` are the extension, the pasted-attachments folder and the workspace folders (`SidebarProvider.resolveWebviewView`); an image outside them has no `src` and the webview reads it once through `readImageFile`. The card (`src/webview/voiceImages.ts`) is a strip of up to four 40px thumbnails and a count ("+N" for the rest); a click opens it to fixed-height tiles (the open cards survive snapshots); a tile shows the image full size over the Bot view, where ←/→ step through the message's images, "Open in editor" opens the file (`openFile`), and Escape, ✕ or the backdrop close it. Thumbnails and tiles have fixed sizes, so loading an image never changes a turn's height.
- **Transcripts** are saved per task in workspaceState by `VoiceTranscriptStore` (`transcriptStore.ts`).
- "Speaking" is based on actual playback reported by the hidden audio page (after Pipecat's BotStarted/StoppedSpeaking); before the first sentence is heard the status shows "synthesizing".

## Division of labor

- The voice agent itself uses `read`, `grep`, `glob` to look at code.
- Questions that need many files go to `research` (a background one-shot `omp -p`, read-only; results are attached in later turns as `<research-result>`).
- Changing code and running commands: small jobs the voice agent does itself; heavy jobs (many files, big refactors, long test runs) it hands to the worker with `tell_worker` (see [Pairing](#pairing)).
- What the user should see rather than hear goes through `show_me` (`markdown`, optional `title`, `board`, `mode`, `block`): short content (no Mermaid, at most 5 lines, no board or mode asked for: `showMeIsCard`) is a "Snippet" card under the reply in the Bot view, open from the start, highlighted when it is one fenced block, with a copy button; everything else is written on a blackboard, a board tab in the editor that the agent points at while it talks ([blackboard.md](./blackboard.md)). Never spoken. It changes no workspace file, so it works in every permission mode, Plan included (but not in proactive turns, like every tool except `worker_status`); markdown over 20000 characters is refused, since the transcript keeps every argument in workspaceState. `board_point` and `board_view` point at and control the boards. Saved transcripts still show the old `show_text` cards.

## Components

- **`WorkerController`** (`workerController.ts`, implemented by `SidebarProvider`) is the only entry point for controlling the worker.
  - `send` routes by worker state at execution time: idle → new task; busy + now → `prompt` with `streamingBehavior:'steer'`; busy + after → the panel's queue.
  - `answer` answers `extension_ui_request` first-come-first-served with the webview (omp tool approvals are also selects).
  - `onTabEvent` / `onActiveTaskChanged` fire from `sendStateSync` and tab events; `onRequestsChanged` fires when pending requests change (`RpcExtensionUiHandler.onDidChangePending`).
  - A tab in TUI mode reports `status().tui`: the voice agent drives the CLI's TUI through the same tools, typing prompts and answers and reading its screen (`readTuiScreen`, `typeIntoTui`); see [tabs-and-tui.md](./tabs-and-tui.md#tui-tabs-and-the-voice-agent).
- **`VoiceLlm`** (`voiceLlm.ts`) is a hidden omp RPC process (`--tools read,grep,glob --approval-mode yolo`). Host tools are registered with `set_host_tools`. One voice session per worker session, switched with `switch_session`.
  - Tool arguments stream: it adds up each host tool call's `toolcall_delta` pieces (the partial message's parsed `arguments` lag behind them in omp's frames) and passes the raw JSON on (`onToolDelta`).
  - A message cut off at the output token limit (`message_end` with `stopReason: "length"`): its host calls are dropped (`onToolDropped`); omp 18.4 and pi 0.99 already fail them themselves (pi's `failToolCallsFromTruncatedMessage`), and one that arrives anyway is answered with an error, never run.
  - `prompt` never rejects: busy, an exited process, a failed `prompt` response, `agent_end` with an error all resolve `{ error }`. An aborted run that has not settled 5 s later (`ABORT_SETTLE_MS`) ends with an error and the process is given up (`onExit`), so the next turn starts a new one instead of waiting forever.
  - `steer(message)` sends omp/pi `steer` into the running prompt: the agent takes it in at its next turn boundary, after the tool calls of the message being written. False when nothing runs or the run is ending.
  - Built-in skill: `grilling` (`BUILTIN_VOICE_SKILLS`, `src/shared/builtinVoiceSkills.ts`) ships in `media/voiceAgent/skills/grilling/SKILL.md` with a `LICENSE` giving its source (MIT). The former `show-me` skill is gone: its ways of drawing (pseudocode, call trees, Mermaid, diffs) are in `show_me`'s description, and its views go on a board instead of files. Built-ins are always loaded, whatever `voiceAgent.skills` says; `resolveVoiceSkills` (`builtinSkills.ts`) puts them first and drops a chosen skill of the same name, so the built-in copy is the one passed.
  - Skills picked in Settings → Voice → "Voice agent" → Skills (`voiceAgent.skills`, where the built-ins show as always-on chips) load on the next process start. omp: `--plugin-dir <extension>/media/voiceAgent` (the folder is laid out as an omp plugin; this adds it to discovery without replacing the user's skill directories) plus `--skills=<built-ins and chosen names>`; omp's own precedence applies, so a same-named skill in the user's `.omp` or `.claude` skills wins over the built-in, one in `.agents` loses. pi: `--no-skills` plus one `--skill <SKILL.md>` each, built-ins included (chosen skills' paths from `sourceInfo.path` of the chat tab's `get_commands`). `--no-skills` on omp only when the list is empty. Research runs without skills.
  - System prompt: `VOICE_SYSTEM_PROMPT` (`voicePrompt.ts`), plus the user's `voiceAgent.extraPrompt`, trimmed, under "Additional instructions from the user:" (`voiceSystemPrompt`); blank adds nothing. The default itself is not editable: it is tied to the host tools, and a stored copy would go stale on updates. A change to the setting calls `VoiceAgent.restartProcess`: between turns, the process stops and starts again with the new prompt, and each task's voice context resumes from its session file. Settings → Voice → "Voice agent" → Instructions edits it (View renders Markdown, Edit is a textarea saved on blur or View) and shows the default read-only under "View default prompt" (`src/webview/settings/voicePrompt.ts`; raw HTML such as `<editor>` shows as text via `renderMarkdownLiteralHtml`).
  - Prompt cache: the system prompt, tool definitions and skills are fixed for the life of the process (a changed prompt restarts it); everything that changes per turn (`<editor>`, `<worker>`, `<tone>`, `<late-result>`, …) is in the turn's user message, after the history the provider has cached. Measured on omp 18.4 with a 12 k-token system prompt: from the second turn on, about 99.7% of the input was a cache read (12 436 of 12 471 tokens).
- **`HostToolRouter`** (`hostTools.ts`) executes `tell_worker` (a `readOnly` task is dispatched directly; a new file-changing task goes through two-step confirmation), `confirm_task`, `stop_worker`, `answer_worker`, `worker_status`, `research`. Proactive turns may only use `worker_status`. Permission tiers for the voice agent's own tools: [permissions.md](./permissions.md#voice-agent-tools). For a TUI tab (`<worker tui="true">`): `worker_status` returns the TUI's screen (`pagesBack` 0-20 reads further up), `answer_worker` takes `value` and `keys` (named keys, `terminalKeys`) instead of a request id and returns the redrawn screen, `stop_worker` presses Escape.
  - **Previews while the model writes a call** (`preview`, `partialFields` in `partialArgs.ts`): an `edit_file` whose `path`, `oldText` (and `nearLine`, if given) are written starts typing `newText` as it streams (`EditorHands.previewEdit`, only while Pi is followed); a `show_me` past a card's size starts drawing its whole blocks on the board it targets (`BoardHands.preview`). Only when the finished call could run unasked: not proactive, not Plan, no approval needed, no worker lock. The schemas put `newText` and `markdown` last so the place and the board are written first. When the call arrives, `execute(…, callId)` adopts its preview if the final arguments match what was typed or drawn (final arguments win: otherwise it is undone and the call runs anew); a call never sent (cut off at the token limit, the reply cut off, skipped by the CLI) has its preview undone (`dropPreview`; `VoiceAgent._runTurn` drops what is left when the turn ends).
- **`WorkerDigest`** (`workerDigest.ts`) compresses worker events into activity log lines, attached to the voice model each turn.
- **`FloorArbiter`** (`floorArbiter.ts`) decides when to speak up proactively: the worker waits for an answer, a TUI tab's run stopped (`stopped`, from `tui_run_end`, carrying the screen's last lines; announced at once, as it may be an approval), an error, stable idle for 4 s after finishing, research completed; with `narration: all`, progress too. `VoiceAgent` asks it every second and whenever requests change. Proactive turns end with `<worker-update>`; a `<silent/>` reply is neither shown nor spoken.
- **`ToneDial`** (`tone.ts`) rolls each turn's `<tone mood time aside>` block, per `voiceAgent.humor` (`off` leaves it out). A model left alone jokes every reply or never and keeps one mood, so the host holds the dice: the mood drifts (30% per turn; late at night it may turn `tired`), an error makes it `sober` for two turns, finished work makes it `pleased` once. An `aside` (a kind of joke: pun, cold joke, mock gravity, …; a callback only after four turns) is invited at 30% (`occasional`) or 55% (`often`), never two turns running and never with a worker request, proposal, pending approval or deletion, failed card, interruption or error. The block goes in the user message, so `VOICE_SYSTEM_PROMPT` stays constant for the prompt cache; its "Tone" section says how to use it, and the user's Instructions set the flavour.
- **`ResearchRunner`** (`research.ts`) runs `research` tasks.

## Voice mode (`VoiceMode`, `voiceMode.ts`)

- A page in hidden Chrome (`--headless=new`, `browserAudio.ts`) does `getUserMedia` (AEC3) and playback, exchanging 16 kHz PCM with the extension over local `ws` (with a random token).
- Silero VAD + `SpeechSegmenter` segment speech. Human speech while the bot is talking counts as barge-in only after STT + `echoFilter` confirm it.
- `conversation.ts` is a pure state machine (`reduce(state, event) → effects`). Each reply has its own `AbortController`; the `prompt` effect calls `VoiceAgent.say(text, 'stt', listener, { signal, interrupted })`.
- **Barge-in or remark** (pi's `Agent.steer`). Speech over the reply's voice (synthesizing or playing) cuts it off at once, as before. Speech while the reply is still silent (thinking, or at its tool calls) cuts nothing yet: the reply's text is held while the user has the floor (`userHolds`). Once the words are in, a short remark (`isRemark`: at most 12 words or 20 CJK characters, no stop word such as "stop", "wait", "no", "等等", "不对") becomes a `steer` effect: `VoiceAgent.steer` sends it into the running reply as `<user source="stt" during-reply="true">`, the transcript records it (`onRemark`), and the held text is spoken. Anything else cuts the reply off and goes out as a new prompt, as does a remark the reply ended too soon to take (`steerFailed`). Typed messages always cut.
- **One way out of a turn**: `VoiceAgent._runTurn` ends every reply (done, cut off, provider or network error, the process dying or hanging) through one `finally`: the turn is cleared, previews of calls never sent are undone, and `listener.onEnd` gets the result once, so voice mode's `llmEnd` always comes and the floor is released. Listener callbacks are guarded (`guardListener`): `PiRpcBridge` drops an event whose handler throws, which could leave a host tool call unanswered and the reply hanging.
- **Listeners never wait.** Everything on the LLM event path returns at once and queues the slow part: text goes through the reducer to `Speaker.enqueue` (TTS and playback run on their own queue), anchors to `AgentCursor._enqueue` and `Blackboards.pointAnchor` (not awaited), host tool calls to `HostToolRouter.execute` (a promise collected in `executing`; edits and drawings return before their animation), the transcript store to a save timer and the Bot view to a 50 ms refresh timer.
- `TtsClient` (`tts.ts`) calls OpenAI-compatible `/audio/speech` (the custom engine sends a Bearer key when it has one, see [voice.md](./voice.md#api-keys)).
  - Custom engine `tts.languageField` sets the language field: `none` (default) sends nothing; `perSentence` sends `language: zh/en` per sentence; `chineseLangCode` splits Chinese/non-Chinese segments and sends `lang_code: z` for Chinese.
  - Empty `tts.model` / `tts.voice` are omitted from requests (the server decides). The settings Test returns the server's `/models` list to pick from.
- **Legacy `tts.provider`** (kept in package.json as deprecated, only so it can be read and removed) is still read when `tts.engine` is unset: `builtin` / `custom` map directly; service-named `chatterbox` / `kokoro` / `openai` read as `custom` + `perSentence` / `chineseLangCode` / `none`, and old chatterbox / kokoro get their historic default model/voice when empty. `migrateTtsSettings` (on activation) writes these values plus `tts.engine` into the original config target and deletes `tts.provider` (targets that already have `tts.engine` only get the delete); workspace before user settings.

### When STT or TTS is unavailable

The voice agent comes online even when STT / TTS cannot be used (design §5.13):

- Before starting, services that failed are checked once more; ones still failing are not passed to `VoiceMode.start` (reason in `VoiceMode.unavailable`, sent to the webview as `VoiceStatus.unavailable`).
- No STT: VAD is not loaded and the audio page runs with `capture=0` (playback only, no mic); the user types.
- No TTS: `ConvState.voiced = false`; replies are text only, never entering synthesizing / speaking.
- Neither: no audio page is opened.
- The phone button stays clickable. Grey tags next to the status text, "Can't hear" / "No voice" (styled like "Muted"; hover shows the reason; click opens Settings → Voice), say what is missing. Mid-session failures only go to the log and a Bot view system message; the conversation continues.
- If the audio page cannot open the mic, `VoiceMode.unavailable.stt` shows why.
- Readiness tracking itself is described in [voice.md](./voice.md#readiness).
- **`VoiceServiceSync`** (`serviceSync.ts`) follows readiness and settings changes while voice mode is on: as soon as a missing service becomes ready it is resolved and attached (`VoiceMode.useTts` speaks from the next reply on — the state machine's `voiced` event applies after the current reply; `useStt` loads VAD and has the audio page open the mic with `{"type":"capture"}`, opening a new audio page if needed), `unavailable` is cleared, and status is resent. A service in use whose settings change is swapped for the new config; on failure it is not torn down and becomes usable once it recovers. No voice agent restart needed.

### Multiple windows

`ActiveVoiceWindow` (`activeWindow.ts`, `globalStorage/voice-windows/<id>.json`: pid + last focus time) decides which window owns voice. Only the window with voice mode on that was focused last listens and speaks; the others stand by (mic off, reply interrupted, status bar Standby).

## Pairing

Full design: [voice-pair-agent-cursor.md](./voice-pair-agent-cursor.md).

- **Editor context.** Each turn carries `<editor>` (`editorSnapshot.ts`: the user's current file, cursor line, visible lines, selection, and selected code with line numbers; `<editor unchanged/>` when identical to the previous turn). Editor tracking is shared with the sidebar via `FileEditorTracker` in `src/utils/fileEditor.ts`.
- **Code anchors.** Anchors in replies, `⟦path:12-20⟧` / `⟦path#name⟧`, are extracted from the text stream by `AnchorStream` in `codeAnchors.ts` (neither shown nor spoken).
- **Agent cursor.** `AgentCursor` (`agentCursor.ts`) shows Pi's focus with end-of-line labels, without touching the user's cursor or focus: pointing while explaining (purple `Pi`), plus files the voice agent reads and files the worker reads/writes (`workerFocus.ts`; written line ranges come from `changedLines` in `piFocus.ts`, comparing content before and after; blue `Pi · reading` / green `Pi · writing`).
  - In voice mode a pointer takes effect when the sentence after the anchor starts playing (`onAnchors` in `voiceMode.ts`); in typed conversation, immediately. A pointer holds for 6 s; read/write activity queues meanwhile.
- **Follow Pi.** Toggled from the status bar `$(eye) Pi: …` or the eye button in the editor title bar (`followPi` / `unfollowPi` / `toggleFollowPi`; setting `voiceAgent.followPi` is the startup default). While following, the editor opens and scrolls to the focus; typing stops following. The host tool `open_file` opens files whether or not following.
- **Acting itself and directing the worker.** The voice agent always has both sets of tools.
  - It acts itself with `edit_file` (`pairHands.ts`: types character by character in the editor, Pi's write highlight follows, one Ctrl+Z undoes the whole edit) and `run_in_terminal` (runs in the "Pi" terminal via shell integration, reading output and exit code).
  - `edit_file` and `show_me` return before their animation: an edit once placed (typed and saved in the background, one queue per file), a board once written with its outline (drawn in the background). The turn can end and the model speaks while they go on. What they find out afterwards (an edit that could not go in or be saved, Mermaid and web page script errors) is handed out once as `<late-result tool="…">` (`HostToolRouter.takeLateResults`), at the end of the next tool result or in the next turn's message. A cut-off reply or stopping voice finishes the typing at once (`HostToolRouter.finishTyping`). Details: [voice-pair-agent-cursor.md §11](./voice-pair-agent-cursor.md#11-working-beside-the-worker-the-file-lock-2026-09-29), [blackboard.md](./blackboard.md).
  - A command's output that moves the cursor or switches to the alternate screen (`drawsScreen`: omp, pi, vim, less, htop) is replayed into a headless xterm (`TerminalRun.screen()`, 200×60, since extensions cannot learn a terminal's size), and `run_in_terminal`'s early return, `terminal_send` and `terminal_read` return its screen as text through `ScreenReader` (`src/pi/terminalScreen.ts`): "no change" when it is what the voice agent last read; `terminal_read` `pagesBack` reads the scrollback, or pages a full-screen program up and back down with PageUp/PageDown. Line output stays cleaned lines, as before; a command that ended is reported from its lines.
  - It directs the worker (`tell_worker`, `confirm_task`, `stop_worker`, `answer_worker`, `worker_status`) for heavy jobs; the prompt's "Dividing the work" section (`VOICE_SYSTEM_PROMPT`) says when.
  - **Worker file lock.** Before each worker tool call it does not block, the permission gate (`src/piExtension/permissionGate.ts`) appends the files the call will change as an NDJSON line to the file named by `VSCODE_PI_EDITS_FILE`. `PermissionGateFile` reads them into `WorkerEditLocks` (`src/pi/workerEdits.ts`), cleared on `agent_end`; `SidebarWorker.lockedPaths` returns the ones overlapping a target, and `HostToolRouter._workerLock` refuses `edit_file`, `create_file`, `rename_file`, `delete_file`, `save_file` on them until the task ends. Other files stay editable.
  - Gaps: TUI tabs do not load the gate, so while a TUI tab runs a task all the voice agent's file changes are refused; `rm`/`mv`/`sed -i` via bash are not reported. Details: [voice-pair-agent-cursor.md §11](./voice-pair-agent-cursor.md#11-working-beside-the-worker-the-file-lock-2026-09-29).

## Names and avatars

Files: `src/voiceAgent/speakers.ts` (`resolveSpeakers`), `src/shared/voiceSpeakers.ts` (`speakerNames`, `parseAvatarSetting`), `src/shared/avatarPresets.ts` (`DEFAULT_AVATAR_PRESETS`, `avatarPresetSrc`, `avatarPresetRows`, `avatarPresetAnimations`, `frameIndex`), `src/webview/avatar.ts` (`avatarMarkup`, `avatarAnimations`), `src/webview/avatarMotion.ts` (`AnimationRun`).

- Settings `voiceAgent.userName` / `userAvatar`, `botName` / `botAvatar` (default names User / Bot; an empty avatar is the otaku for you, `preset:otaku`, and the gentleman for the voice agent, `preset:gentleman`, by `DEFAULT_AVATAR_PRESETS`; the line icons stay selectable as `preset:user` and `preset:robot`; empty name falls back to default; max 40 characters).
- An avatar is one of:
  - a preset `preset:<id>`: the line icons `user` / `robot` (`ICON_PRESETS`), or pixel art (`avatarPresets.ts`: uncle / boy / cat / otaku / woman / gentleman; each a 16×16 character pixel map + palette, merged per row into `<rect>`s and drawn as a 64px SVG with `shape-rendering: crispEdges`, transparent background so the frame color shows);
  - an emoji or up to two characters (split by grapheme);
  - an image path (contains a slash, starts with `~`, or has an image extension; `~` is home, relative paths start from the first workspace folder; ≤2 MB).
- The host reads images as data URIs; `VoicePanel` sends them in a separate `speakers` message to the webview (whether or not the Bot view is shown; on config change, view show, and webview `ready`; deduplicated by object reference). The webview crops them to a 64px square PNG with canvas and reuses one markup string for all turns. The voice agent's avatar also replaces the robot button (16px) in the status bar above the composer, and its name is that bar's label while the agent is offline (`setVoiceBarBot`). That button shows where a click leads: in the Bot view it is π and the tab's backend (`OMP` / `Pi`, `setBotViewShown`), the way back to the worker; voice mode then shows in the status dot, the bar's tint and the tooltip. Unreadable images and unknown presets fall back to the speaker's line icon (`DEFAULT_AVATAR`), which also shows until the avatars arrive.
- Settings → Voice → "Voice agent" → "Names and avatars" shows previews, reasons, and clickable presets; the speaker's default preset is the empty setting's tile (the line icons are `preset:user` / `preset:robot` tiles, their labels and the pixel labels say whose default each is). Upload opens a file dialog via `pickAvatar`, which answers `avatarPicked` with the picture read; like a preset picked, it is an unsaved edit until the page's Save.
- The voice agent's avatar moves (`src/webview/avatarMotion.ts`, CSS in `styles/chat/voiceBar.css`): every `.av-motion` element. Only one avatar on screen has it: with the Bot view shown, the avatar of the reply being read aloud (Alt+click; `sentenceActions.replay.entryId`, the group header turn's avatar of that assistant entry), else of the latest reply (`voicePanel.ts` `placeLiveAvatar`: the group header turn's avatar when the last entry is an assistant entry, so it is on while the reply thinks and speaks, and moves off once the user speaks); otherwise the voice bar's robot (`voiceBar.ts` `render` toggles it with `botViewShown`). Speaking: the bot's `voiceLevel` (one per 64 ms of audio; `ClipLevelMeter` in `src/voiceAgent/botLevel.ts`, used by voice mode's reply speaker and by `ReplayPlayer` for sentences read aloud, voice mode on or off, from each clip's start report; a pause or stop reports 0) is remapped from 0.5..0.9 (TTS speech sits at level 0.67 and up, so syllables only show within that range) to 0..1, smoothed into `--talk`; `.talking` is set while the voice has made sound within 600 ms, and an avatar that stops being `.av-motion` mid-sentence is put back at rest. Thinking (`.voice-bar` or `.vp` with `data-state="thinking"`): the robot (`ICON_ROBOT`, `.av-robot`) keeps its head outline, antenna and ears; its eyes (`.av-eyes`) hide and a nested SVG screen inside the head (`.av-screen`, hidden by its `visibility` attribute so other pages never show it) shows log lines (`.av-log`) that scroll up one line at a time (8 units in 4 steps) and flicker (static under `prefers-reduced-motion`). A pixel preset plays its own animation (next item); an uploaded picture or text is not drawn over while thinking.
- Each pixel-art preset has its own thinking animation (`think` in `avatarPresets.ts`), and the otaku and the gentleman a talking one (`talk`). An animation is tracks, parts that change on their own: each has states (the rows that differ from the resting map; a frame changes the pixels where a state's rows differ from it, later tracks winning) and a `pick`: `loop` (a fixed `[state, ms]` list from the animation's start), `random` (another state after a random hold), `level` (talking: how many of `steps` `--talk` reaches, mouth closed below 0.25, half below 0.6, open above) or `syllable` (talking: 0 while the mouth is closed, a weighted random state each time it opens); `rows` change all along it. Thinking: the boy scratches his head, the woman looks up at a thought bubble over her head that fills with dots one by one, the uncle holds a red mug of coffee with steam curling up beside his face, the otaku's pupils walk a small ring in the middle of each lens (150 ms a step), the cat dozes off (eyes shut, z then Z, head nodding), the gentleman's brows go up and down each on its own (random), his eyes look left and right (switching about every 800 ms), a glint runs round his monocle and his moustache twitches, its curled tips flattening for a moment. Talking: the mouth follows `--talk` in three steps; the gentleman's left moustache tip lies flat, his eyes stay still, and about one syllable in five raises one brow, the right or the left (weights 8 : 1 : 1 for rest, right, left), never both, dropping again when the mouth closes; the otaku glances left and back every 0.5–1.2 s. The host resolves them into `VoiceAvatar.think` / `talk` (`avatarPresetAnimations`: a frame, as an SVG data URI, for every combination of the tracks' states, at `frameIndex`); `avatarMarkup` scales each frame like the picture, decodes them ahead, keeps them by the picture's `src` (`avatarAnimations`; not in the markup, which every turn repeats) and marks the `<img data-animated>`. `avatarMotion.ts` swaps the `.av-motion` picture's `src`, each animation played by an `AnimationRun` per picture: talking while `.talking` (every animation frame, by `--talk`), else thinking (`setAvatarThinking`, called from `voiceBar.ts` `render` with the voice bar's `data-state`; on a timer, at most 250 ms apart, so an avatar that becomes `.av-motion` mid-thought joins in), else at rest, also when it stops being `.av-motion`; under `prefers-reduced-motion` it stays still. The robot keeps its CSS log screen; other pictures and text do not move while thinking.
